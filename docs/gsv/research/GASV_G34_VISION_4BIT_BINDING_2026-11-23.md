## Місток до тексту (G40, 2026-11-24)

Знайдено ключову геометричну відповідність: `mmproj-model-f16.gguf`
(проектор **MiniCPM-V-4.7-1B**) має `projection_dim = 1024`, а локально
запускне текстове ядро `MiniCPM-V-4_7-1B-Q4_K_M.gguf` має `d_model = 1024`.
Тобто це єдина пара «vision + text», що може дати image→text на цьому боксі
(35B Q4-ядро — 19.7 ГБ і не запускається при 7.7 ГБ RAM).

- Квантовано 1B-проектор у Q4_K: `minicpm1b-vision-q4k.gguf` (308 955 964 B).
- `cargo xtask vision-forward --out <f32>` експортує повний vision-вектор +
  `gsv.vision-prefix.v1` JSON (dim/sha256/sanity), а не лише перші 8 чисел.
- У `rusty-engine` додано PH-1204 plumbing: `Q35Decoder::step_hidden` /
  `step_embedding` / `prefill_embeddings`, поле `vision_prefix` у
  `TextRunner35`, `--vision-prefix <f32>` для `rusty run|serve`; state-cache
  обминається при наявності префікса (інакше текстовий cache hit тихо
  з'їдав би зображення). `cargo xtask check` зелений.
- **Чесна перевірка:** `--vision-prefix` справді змінює генерацію, але
  1-блоковий вектор дає вироджений текст (`Hathathatha...`), тоді як
  нульовий 1024-вектор дає цілком зв'язний рядок. Механізм працює,
  **якість залежить від повноти vision-фіч**: запущено повний 27-блоковий
  прогон 1B-проектора з `--out`, але він зірвався на блоці 0
  (`g-3289`, hub перестав відповідати) — `MemFree` впав до ~64 МБ. Повний
  глибинний вектор заблокований RAM хоста; сам plumbing працює.
- **G41:** додано per-block checkpoint/resume (`gsv.vision-checkpoint.v1`,
  `--checkpoint` / `--resume`) — стан токенів зберігається після кожного блоку
  атомарно, тому перезапуск хаба не втрачає вже зроблені блоки. Жива перевірка:
  етап 1 (блоки 0–1) записав `data/vision_prefix_1b_cp.json` (`next_block=2`),
  етап 2 з `--resume` зірвався на новому збої хаба, але контрольна точка лишилась
  цілою на блоці 2. `MemFree` у момент збою — ~10 МБ.
- Після відновлення RAM resume-етапи 4/8/12/15/18 завершились `EXIT=0`,
  контрольна точка дійшла до **18/27 блоків**. Етап 21 знову зірвався на
  збої хаба (`MemFree ~105 МБ`), але стан збережено на блоці 18 — наступна
  сесія може продовжити прямо з нього, не перераховуючи перші 18 блоків.
- **G42:** пір іноді повертає порожній partial (`weights_matvec task returned
  no partial vector`, `g-3785`/`g-3788`), через що група ніколи не завершується.
  `matvec_inner` тепер робить до 3 спроб: бачить failed-шард у `mesh.tasks`
  одразу, переставляє нову групу, а також повторює при коротких partial.
  Щоб не чекати ручного запуску, створено automation
  `aut_20ed16930001BQfnRJtPimxtkS` (кожні 20 хв, expires 8 год, fast-fail 180 c; замінила
  shell-автоматизацію, яку зламав PowerShell quoting): вона читає
  `next_block` із checkpoint, відновлює по 3 блоки й пише повний 1024-вектор

### G43 — end-to-end `vision-chat` (2026-11-25)

`cargo xtask vision-chat` поєднує обидві половинки в одну команду:
зображення → Q4_K vision forward на кластері (`--image-tokens N`) → експорт
1024-векторів → `rusty run --vision-prefix <f32> --vision-at N` → текстова
відповідь. `--prompt-file` уникає обрізання промпта шеллом; префікс `[N]` rusty
прибирається з відповіді.

Живий smoke: `gsv-hero.png`, 1 блок, 4 токени, **119 cluster ops**, 1018 c,
`ok=true`; відповідь *"In the image, there is a man wearing a black shirt…"*.
Це не доведення image-grounding — скоріше за все галюцинація; жодного
quality-claim. Повний 27-блоковий 4-токенний прогон (~6 год) запущено
2026-11-25 поетапно з окремим checkpoint `data/vision_prefix_1b_mt4_cp.json`:
етап 3 завершився `EXIT=0` (2591 c, `next_block=3`), етапи 6…27 ідуть у фоні;
результат пишеться у `vision_prefix_1024_mt4_full.f32`. Тикет G44
`in_progress`. Після завершення — порівняння з 1-блоковим mt4 і нульовим
baseline через `rusty --vision-prefix --vision-at 3`.
